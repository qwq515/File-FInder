This morning I debugged a cache inconsistency issue in a small API service. 
The symptom was simple: after a user updated a profile record, the API sometimes returned stale data for several seconds. 
English and numeric fields were usually correct, but display names and descriptions were occasionally out of date. 
The database itself looked fine, so the problem was almost certainly in the caching layer.
I started by checking the Redis keys. 
The service used a key pattern like user:profile:{id} with a TTL of 300 seconds. 
On update, the code wrote to the database and then called cache.delete(key). 
That sequence looked correct, but the logs showed a race condition. 
A read request could repopulate the cache with the old database row between the update transaction and the delete call. 
Under low traffic the window was tiny, but under concurrent requests it was wide enough to reproduce.
I added temporary logging around cache.get, cache.set, and cache.delete, including request IDs and timestamps. The logs confirmed the race: one request read the old row and wrote it back to Redis after the delete had already run. 
I then tried a versioned-key approach. Instead of deleting the cache entry, the update path incremented a version field and wrote a new key such as user:profile:{id}:v2. 
Readers always fetched the current version from a small metadata key. This removed the delete race entirely.
After the change, I ran a load test with 200 concurrent update and read requests. 
Stale reads dropped from about 3 percent to zero in a ten-minute run. I also added a metric for cache hit rate and a warning log when the metadata version and data key disagree. 
The fix was small, but the debugging process reminded me to verify assumptions with logs instead of trusting the intended code path. 
Tomorrow I will add a regression test that simulates the read-repopulate-delete interleaving, so this bug does not return silently.
