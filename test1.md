Yesterday I spent several hours debugging a tokenizer pipeline that handles mixed Chinese and English input. The model itself was not the problem. The preprocessing stage was producing inconsistent tokens, and that instability was enough to confuse every downstream component. For example, a short Chinese phrase meaning "debug mode is enabled" should ideally become four clean tokens: the English word "debug" followed by three Chinese units. Instead, the tokenizer returned "de", "bug", one Chinese character, a merged Chinese unit, and another Chinese unit. That split looked harmless at first, but it changed sequence length, broke alignment, and reduced the F1 score on the mixed test set from 0.81 to 0.72.

I first checked config.json and found that tokenizer_type was set to bert-base-chinese. That choice works well for Chinese text, but it is not always sensitive to English subword boundaries. I then tried a regex-based splitter: re.split(r'([\u4e00-\u9fff]+|[A-Za-z]+|\d+)', text). This worked for most clean inputs, but it failed on emojis, URLs, and punctuation such as https://example.com/debug?id=42. When the regex produced empty strings, I added a fallback to jieba.lcut plus whitespace splitting for English. After that change, the F1 score recovered to 0.81, and unknown_token_ratio dropped from 0.14 to 0.06.

One edge case remains: Chinese commas and English commas are treated as different tokens, which can still confuse the downstream model. Tomorrow I will write a pytest unit test with 100 mixed samples and log token_count and unknown_token_ratio for each case. I also need to measure memory usage with batch_size=32. The lesson is simple: print tokenizer.encode(text) before trusting any pretty-printed output. A small preprocessing bug can look like a model failure, but the real fix is often in the pipeline. I will also compare the fallback path against the regex-only path on a separate validation set.
